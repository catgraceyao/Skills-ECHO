# 一、分润算法数学公式

## 1.1 核心参数定义

| 参数 | 符号 | 默认值 | 说明 |
|------|------|--------|------|
| 交易金额 | $T$ | - | 用户购买使用权支付的金额 |
| 平台手续费率 | $\phi$ | 10% | 平台运营成本抽取比例 |
| 直接创作者分成率 | $\alpha$ | 40% | 被购买作品的创作者获得比例 |
| 上游分润池比例 | $\beta$ | 50% | 分配给所有上游创作者的总池 |
| 原创者基础激励 | $\gamma$ | 25% | 引用链末端原创者的最低保障比例 |
| 衰减系数 | $\delta$ | 0.7 | 每上升一层，分配比例的衰减因子 |

## 1.2 分层收益计算公式

### 第一步：计算各层级分配基数

$$T_{net} = T \times (1 - \phi)$$

其中 $T_{net}$ 为扣除平台手续费后的净收益池。

### 第二步：直接创作者收益

$$R_0 = T_{net} \times \alpha$$

$R_0$ 为被购买作品创作者（层级 0）的收益。

### 第三步：上游分润池计算

$$P_{upstream} = T_{net} \times \beta$$

### 第四步：层级权重分配

对于一条包含 $n$ 层上游引用的链条（不含直接创作者），各层级的权重为：

$$w_i = \delta^{i-1}, \quad i = 1, 2, ..., n$$

其中 $i=1$ 表示最近的上游（父作品），$i=n$ 表示原始创作者。

### 第五步：权重归一化与收益计算

$$W = \sum_{i=1}^{n} w_i = \sum_{i=1}^{n} \delta^{i-1} = \frac{1 - \delta^n}{1 - \delta}$$

各上游层级实际收益：

$$R_i = P_{upstream} \times \frac{w_i}{W} = P_{upstream} \times \frac{\delta^{i-1} \times (1 - \delta)}{1 - \delta^n}$$

### 第六步：原创者保障机制

若链条过长导致原创者收益过低，启用保底机制：

$$R_n' = \max(R_n, T_{net} \times \gamma)$$

若触发保底，从其他上游层级等比例扣除差额。

## 1.3 简化计算公式（实用版）

对于快速计算，使用以下简化公式：

```
总收益池 = 交易金额 × 90% (扣除10%平台费)

直接创作者收益 = 总收益池 × 40%
上游分润池 = 总收益池 × 50%

上游层级分配 (i=1,2,3...):
  层级收益 = 上游分润池 × (0.7^(i-1) / Σ(0.7^(k-1)))

原创者最低保障 = 总收益池 × 25% (若计算值低于此数)
```

## 1.4 分叉处理机制

当作品被分叉引用时（多条分支），每条分支独立计算收益：

$$R_{asset}^{total} = \sum_{j=1}^{m} R_{asset, branch_j}$$

其中 $m$ 为包含该资产的分支数量，各分支收益独立计算后累加。

# 二、场景数值分配表

## 2.1 场景 A: 简单引用

### 场景描述
- Alice 原创一首曲（Asset A）
- Bob 引用 Asset A 创作 Remix（Asset B）
- Carol 支付 100 元购买 Asset B 的使用权

### 分配计算

| 步骤 | 计算 | 金额 |
|------|------|------|
| 交易金额 | $T$ | 100.00 |
| 平台手续费 (10%) | $100 \times 10\%$ | 10.00 |
| 净收益池 | $100 - 10$ | 90.00 |
| Bob (直接创作者, 40%) | $90 \times 40\%$ | **36.00** |
| 上游分润池 (50%) | $90 \times 50\%$ | 45.00 |
| Alice (上游第1层) | $45 \times 100\%$ | **45.00** |
| 系统储备 (10%) | $90 \times 10\%$ | 9.00 |

**分配结果：**

| 角色 | 资产 | 层级 | 收益 | 占比 |
|------|------|------|------|------|
| Alice | Asset A | 上游原创 | 45.00 | 45% |
| Bob | Asset B | 直接创作者 | 36.00 | 36% |
| 平台 | - | - | 10.00 | 10% |
| 系统储备 | - | - | 9.00 | 9% |
| **总计** | | | **100.00** | **100%** |

**分析：** Alice 作为原创者获得 45%，高于 Bob 的 36%，体现了对原创的保护。

## 2.2 场景 B: 链式引用

### 场景描述
- Alice 原创（Asset A）
- Bob 引用 A 创作 B
- Charlie 引用 B 创作 C
- David 引用 C 创作 D
- Eve 支付 100 元购买 Asset D 的使用权

### 分配计算

引用链：A ← B ← C ← D（Eve 购买 D）

**参数计算：**
- 净收益池：$100 \times 90\% = 90$ 元
- David (直接创作者)：$90 \times 40\% = 36$ 元
- 上游分润池：$90 \times 50\% = 45$ 元

**上游层级权重计算（δ = 0.7）：**

| 层级 | 创作者 | 资产 | 权重 $w_i = 0.7^{i-1}$ |
|------|--------|------|------------------------|
| 1 | Charlie | C | $0.7^0 = 1.000$ |
| 2 | Bob | B | $0.7^1 = 0.700$ |
| 3 | Alice | A | $0.7^2 = 0.490$ |
| **总权重** | | | **2.190** |

**各层级收益：**

| 层级 | 创作者 | 权重占比 | 计算 | 收益 |
|------|--------|----------|------|------|
| 1 | Charlie | 1.000/2.190 | $45 \times 45.66\%$ | 20.55 |
| 2 | Bob | 0.700/2.190 | $45 \times 31.96\%$ | 14.38 |
| 3 | Alice | 0.490/2.190 | $45 \times 22.38\%$ | 10.07 |

**原创者保障检查：**
- Alice 计算收益：10.07 元
- 最低保障：$90 \times 25\% = 22.50$ 元
- 触发保底，Alice 获得：22.50 元
- 差额：$22.50 - 10.07 = 12.43$ 元
- 从 Charlie 和 Bob 等比例扣除（按原比例 45.66:31.96）

**调整后的上游分配：**

| 创作者 | 调整前 | 扣除 | 调整后 |
|--------|--------|------|--------|
| Charlie | 20.55 | 7.31 | 13.24 |
| Bob | 14.38 | 5.12 | 9.26 |
| Alice | 10.07 | +12.43 | 22.50 |

### 最终分配结果

| 角色 | 资产 | 层级 | 收益 | 占比 | 说明 |
|------|------|------|------|------|------|
| Alice | Asset A | 原创者 | 22.50 | 22.5% | 触发保底 |
| Bob | Asset B | 上游第2层 | 9.26 | 9.3% | - |
| Charlie | Asset C | 上游第1层 | 13.24 | 13.2% | - |
| David | Asset D | 直接创作者 | 36.00 | 36.0% | - |
| 平台 | - | - | 10.00 | 10.0% | 手续费 |
| 系统储备 | - | - | 9.00 | 9.0% | - |
| **总计** | | | **100.00** | **100%** | |

**链式分配可视化：**

```
Eve 支付 100 元
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 平台手续费: 10.00 元 (10%)                          │
├─────────────────────────────────────────────────────┤
│ 净收益池: 90.00 元                                  │
│ ├─ 直接创作者 (David): 36.00 元 (40%)              │
│ ├─ 上游分润池: 45.00 元 (50%)                      │
│ │   ├─ Alice (原创者): 22.50 元 ★保底             │
```

## 2.3 场景 C: 分叉引用

### 场景描述
- Alice 原创（Asset A）
- Bob 引用 A 创作 B
- Carol 引用 A 创作 C（不经过 B）

这是一个分叉结构，Asset A 是两条独立分支的共同祖先。

### 收益计算逻辑

分叉场景下，各分支独立计算，原创者收益累加：

**分支 1 收益（B 被购买时）：**
- 当用户购买 Asset B，Alice 作为 B 的上游获得收益
- 分配比例同场景 A

**分支 2 收益（C 被购买时）：**
- 当用户购买 Asset C，Alice 作为 C 的上游获得收益
- 分配比例同场景 A

**独立计算示例：**

假设用户 X 购买 B（支付 100 元），用户 Y 购买 C（支付 100 元）：

**分支 1（购买 B）：**

| 角色 | 收益 | 计算说明 |
|------|------|----------|
| Alice | 45.00 | 上游分润池 100% |
| Bob | 36.00 | 直接创作者 40% |
| 平台 | 10.00 | 手续费 10% |
| 系统 | 9.00 | 储备 10% |

**分支 2（购买 C）：**

| 角色 | 收益 | 计算说明 |
|------|------|----------|
| Alice | 45.00 | 上游分润池 100% |
| Carol | 36.00 | 直接创作者 40% |
| 平台 | 10.00 | 手续费 10% |
| 系统 | 9.00 | 储备 10% |

### 分叉原创者累计收益

| 角色 | 分支1收益 | 分支2收益 | 累计收益 | 占比 |
|------|-----------|-----------|----------|------|
| Alice | 45.00 | 45.00 | **90.00** | 45% |
| Bob | 36.00 | 0 | **36.00** | 18% |
| Carol | 0 | 36.00 | **36.00** | 18% |
| 平台 | 10.00 | 10.00 | **20.00** | 10% |
| 系统 | 9.00 | 9.00 | **18.00** | 9% |
| **总计** | | | **200.00** | 100% |

### 分叉结构可视化

```
                    ┌──────────────────┐
                    │   Alice (Asset A) │
                    │    原创者          │
                    │   累计收益: 90     │
                    └────────┬─────────┘
                             │
               ┌─────────────┴─────────────┐
               │                           │
               ▼                           ▼
        ┌──────────────┐           ┌──────────────┐
        │ Bob (Asset B) │           │Carol(Asset C)│
        │  收益: 36      │           │  收益: 36    │
        └──────┬───────┘           └──────┬───────┘
               │                           │
               ▼                           ▼
        用户购买 B                    用户购买 C
        (支付 100)                    (支付 100)
```

**分叉收益特点：**
1. 原创者 Alice 从每条分支都能获得收益，鼓励创作优质原创内容
2. Bob 和 Carol 的收益互不影响，各自发展自己的分支
3. 分叉越多，原创者累计收益越高，形成正向激励

```typescript
interface Creator {
  name: string;
  level: number; // 0 = 直接创作者, 1+ = 上游层级
}

interface DistributionResult {
  creator: string;
  level: number;
  amount: number;
  percentage: number;
  isGuaranteed: boolean;
}

function calculateDistribution(
  transactionAmount: number,
  chain: Creator[],
  params: {
    platformFee: number;      // 0.10
    directCreatorShare: number; // 0.40
    upstreamPool: number;     // 0.50
    creatorGuarantee: number; // 0.25
    decayFactor: number;      // 0.70
  }
): DistributionResult[] {
  const netPool = transactionAmount * (1 - params.platformFee);
  const directCreatorAmount = netPool * params.directCreatorShare;
  const upstreamPool = netPool * params.upstreamPool;
  const reserve = netPool * (1 - params.directCreatorShare - params.upstreamPool);
  
  // 计算上游权重
  const upstream = chain.filter(c => c.level > 0).sort((a, b) => a.level - b.level);
  const weights = upstream.map((_, i) => Math.pow(params.decayFactor, i));
  const totalWeight = weights.reduce((a, b) => a + b, 0);
  
  // 计算各层级收益
  let results: DistributionResult[] = [];
  
  // 直接创作者
  results.push({
    creator: chain.find(c => c.level === 0)?.name || 'Unknown',
    level: 0,
    amount: directCreatorAmount,
    percentage: (directCreatorAmount / transactionAmount) * 100,
    isGuaranteed: false
  });
  
  // 上游创作者
  let upstreamResults = upstream.map((creator, i) => ({
    creator: creator.name,
    level: creator.level,
    amount: upstreamPool * (weights[i] / totalWeight),
    percentage: 0,
    isGuaranteed: false
  }));
  
  // 原创者保底检查
  const originalCreator = upstreamResults[upstreamResults.length - 1];
  const guaranteeAmount = netPool * params.creatorGuarantee;
  
  if (originalCreator && originalCreator.amount < guaranteeAmount) {
    const deficit = guaranteeAmount - originalCreator.amount;
    originalCreator.amount = guaranteeAmount;
    originalCreator.isGuaranteed = true;
    
    // 从其他上游扣除差额
    const others = upstreamResults.slice(0, -1);
    const othersTotal = others.reduce((a, b) => a + b.amount, 0);
    
    others.forEach(creator => {
      const deduction = deficit * (creator.amount / othersTotal);
      creator.amount -= deduction;
    });
  }
  
  // 计算百分比
  upstreamResults.forEach(r => {
    r.percentage = (r.amount / transactionAmount) * 100;
  });
  
  results = results.concat(upstreamResults);
  
  // 添加平台和系统
  results.push({
    creator: '平台',
    level: -1,
    amount: transactionAmount * params.platformFee,
    percentage: params.platformFee * 100,
    isGuaranteed: false
  });
  
  results.push({
    creator: '系统储备',
    level: -1,
    amount: reserve,
    percentage: (reserve / transactionAmount) * 100,
    isGuaranteed: false
  });
  
  return results;
}
```

# 四、经济模型优缺点分析

## 4.1 模型优势

### 4.1.1 激励原创创作
- **原创者保底机制**确保即使引用链很长，原创者仍能获得可观收益
- 场景 B 中，即使 Alice 是第 3 层上游，仍获得 22.5% 的收益（超过直接创作者的 50%）

### 4.1.2 鼓励二次创作
- 直接创作者获得 40% 的高比例，激励基于他人作品进行创新
- 分叉机制让同一原创可以激发多条创新链，形成创作生态

### 4.1.3 收益透明可预测
- 数学公式清晰，创作者可提前计算预期收益
- 分层衰减机制符合直觉：越近的上游贡献越大

### 4.1.4 抗长尾稀释
- 保底机制防止链条过长导致原创者收益趋近于零
- 指数衰减比线性衰减更公平地处理长链条

### 4.1.5 平台可持续发展
- 10% 手续费覆盖平台运营成本
- 10% 系统储备用于生态建设和突发事件

## 4.2 潜在问题与风险

### 4.2.1 收益稀释问题

**问题描述：**
当引用链过长时，中间层创作者的收益会被大幅压缩。

**场景示例：**
假设引用链长度为 10，衰减系数 0.7：

| 层级 | 理论收益 | 占上游池比例 |
|------|----------|--------------|
| 第1层 | 31.4% | 最高 |
| 第5层 | 7.5% | 中等 |
| 第9层 | 1.8% | 极低 |

**影响：**
- 中间层创作者可能感觉收益不匹配其创作投入
- 长链创作的动力不足

**缓解方案：**
1. 设置中间层最低收益保障（如每层不低于 5%）
2. 引入「贡献度系数」，根据作品的实际被引用次数调整权重
3. 允许创作者设置「引用门槛」，只有达到一定使用量的作品才触发分润

### 4.2.2 原创者收益过高风险

**问题描述：**
保底机制可能导致原创者收益超过直接创作者，抑制二次创作积极性。

**示例对比：**
| 角色 | 收益 | 投入 |
|------|------|------|
| 原创者 | 22.50 | 创作原始作品 |
| 直接创作者 | 36.00 | 创作+推广 |
| 中间层 | 9.26 | 多层创作 |

**潜在问题：**
- 直接创作者可能感觉「为他人做嫁衣」
- 更愿意原创而非引用，降低生态活跃度

**缓解方案：**
1. 动态调整保底比例，根据市场反馈优化
2. 引入「创作难度系数」，复杂 Remix 获得更高权重
3. 设置「原创者收益上限」，防止过度保护

### 4.2.3 分叉收益不公

**问题描述：**
分叉结构下，原创者从每条分支获得收益，可能导致「躺赚」现象。

**示例：**
- Alice 原创作品被 100 人引用创建分支
- 每个分支每月产生 100 元交易
- Alice 每月被动收入：$100 \times 45\% \times 100 = 4500$ 元

**潜在问题：**
- 原创者缺乏动力持续创作新作品
- 新创作者难以撼动早期热门原创的地位

**缓解方案：**
1. 设置「原创者收益递减」机制：同作品累计收益超过阈值后，分成比例下降
2. 引入「时间衰减」：作品发布越久，原创者分成比例逐步降低
3. 设立「创作者活跃度奖励」，持续创作的原创者获得额外加成

### 4.2.4 参数调节困难

**问题描述：**
5 个核心参数相互影响，找到最优组合具有挑战性。

**参数敏感度分析：**

| 参数 | 变化范围 | 对原创者影响 | 对直接创作者影响 |
|------|----------|--------------|------------------|
| 平台费率 | 5%-20% | 中 | 中 |
| 直接创作者分成 | 30%-50% | 高 | 极高 |
| 上游分润池 | 40%-60% | 极高 | 高 |
| 原创者保底 | 15%-35% | 极高 | 低 |
| 衰减系数 | 0.5-0.9 | 高 | 低 |

**缓解方案：**
1. 建立参数模拟器，A/B 测试不同组合
2. 引入 DAO 治理，让社区投票决定参数调整
3. 分阶段实施，观察市场反馈后再调整

### 4.2.5 套利与攻击风险

**潜在攻击场景：**

**场景 1：自引用套利**
- Alice 创建 Asset A
- Alice 用另一个账号创建 Asset B 引用 A
- Alice 自己购买 B，获取上游分润

**场景 2：虚假交易刷量**
- 创作者通过虚假交易抬高作品使用量
- 骗取更高的分润权重

**场景 3：链式分叉攻击**
- 恶意创建大量分支，稀释某原创者的收益份额

**缓解方案：**
1. 引入身份验证和 KYC，限制多账号套利
2. 设置「冷却期」，新作品需要一定时间才能获得分润资格
3. 引入「信誉分」系统，异常交易行为降低权重
4. 使用链上数据分析，识别和惩罚刷量行为

# 五、结论与建议

## 5.1 模型总结

Echo Protocol 的多层级分润经济模型通过以下创新解决了创作者经济的核心问题：

1. **透明可预测**：数学公式确保每笔交易的分润都可事先计算
2. **原创保护**：保底机制确保原创者利益不因链条过长而稀释
3. **创作激励**：高比例直接创作者分成鼓励二次创作
4. **生态友好**：分叉机制让优质原创可以衍生出丰富的创作生态

## 5.2 实施建议

### 阶段一：MVP 上线（1-2 个月）
- 实施基础分润算法（不含保底机制）
- 支持简单引用和链式引用
- 上线基础版收益计算器

### 阶段二：功能完善（3-6 个月）
- 引入原创者保底机制
- 支持分叉引用计算
- 上线完整版收益计算器

### 阶段三：治理优化（6-12 个月）
- 参数 DAO 治理
- 动态调整机制
- 高级分析工具

## 5.3 关键指标监控

建议持续监控以下指标：

| 指标 | 健康范围 | 预警阈值 |
|------|----------|----------|
| 原创者/引用者收益比 | 1:1.5 至 1:2 | < 1:1 或 > 1:3 |
| 平均引用链长度 | 2-4 层 | > 6 层 |
| 分叉作品占比 | 20%-40% | < 10% 或 > 60% |
| 平台手续费收入 | 覆盖成本 + 20% | < 成本 |
